# DECISIONS
Ambiguities resolved without asking (simplest option).

1. Subagents: agent files copied from the prototype and adapted to TypeScript into .claude/agents. Spawned through the generic agent tool with the model set per policy (haiku/sonnet/opus).
2. No art assets exist in the prototype (data/ has only JSON; build/web has the Godot export). Tiles are flat colors from prototype tiles.json, with a few deterministic speckles ("flecks") like the prototype.
3. Sim runs at a fixed 60 Hz in shared; the server loop is 30 Hz and runs 2 sim ticks per server tick (keeps the 30 Hz requirement, avoids tunnelling at 20 t/s glide). Snapshots go out at 30 Hz or less.
4. Architect's plan picks overridden by the prompt: heal = 50% max HP; five upgrades as specified (not drill/armor/engine); tile set limited to the nine listed (no basalt/iron/silver/sulphur).
5. Fuel/cargo removed. Pod half-size 23/64 so flush positions sit on the 1/1024 quantisation grid. Lava and rock probability capped (0.2/0.3) so deep terrain stays diggable. Heal probability tuned empirically to ~1 per 400 tiles.
6. Buying max HP also raises current HP by 20.
7. Client (WP2, apps/client): local mode behind a `GameSession` interface (`LocalSession`); WP3 swaps in a networked one. Respawn (3 s dead) and invulnerability (3 s) live in the client session, not shared: while dead the pod is not stepped (world/sand keep running); invulnerability sets hull to a huge value for the tick so shared damage/death logic cannot kill, then restores it (heal pickups kept). A server-authoritative version will need these timers moved into shared.
8. F3 live tuning mutates the `T` object at runtime (cast away `as const`) for a dev-only list of constants the shared code reads live (gravity, thrust, moveSpeed, ...). Module-cached constants (podHalf, DT, QUANT) are not tunable. Affects local mode only.
9. Random respawn: random column in 1..94 (also the first spawn), hashed from (seed, player id, spawn salt); the sim bumps the salt on every death and the client passes a per-session starting salt. The pod rests on the first solid tile scanning down from row 0, so surface pockets never matter.
10. Upgrades are endless (no max level): level L costs floor(50 * 1.6^L), built into tables with iterative multiplication (no pow). Levels are clamped to 200 for lookups and purchases (50 * 1.6^200 is about 5e41, still finite). Five upgrades: drill (dig time x0.9^L, 12-tick floor), max HP (+20), move speed (+8%/level, capped at x2.5), armor (damage x0.9^L, never 0), radar cooldown (x0.9^L, floor 1 s). The ore value upgrade is gone.
11. Ore value scales with depth: floor(base * (1 + 0.01 * row)) in integer math, for wallet and score; heal gives nothing.
12. Light (client only): radius 14 tiles for depth row <= 8, linear to 3 tiles at row 200, constant below; outside is 96% dark with a 1.5-tile soft edge, drawn as one radial-gradient fill per frame. Radar highlights are drawn after the darkness.
13. Radar (Space, which no longer thrusts; W/Up still do): scans ore within 12 tiles (copper, gold, gem, heal, and ore hidden in sand via aux) with shared scanOre into a preallocated Int32Array; highlights last 4 s, ring animation 0.6 s; cooldown 10 s x 0.9^level, min 1 s, kept in Player.radarTicks (decremented per sim tick) and reset on death. Other players' pods are not in LocalSession; when networked sessions add them they must be drawn only within lightRadius.

## WP3 (server + networking)
14. Respawn and invulnerability live in shared `SimPlayer` (`deadTicks`, `invulnTicks`, `finalScore`); this supersedes decision 7. Death resets the run immediately (high score banked), dead pods are not stepped and are ignored by sand, the pod re-spawns (hashed column, new salt per death) after `T.respawnTicks`, then `T.invulnTicks` without damage. Invulnerable pods are still hit-tested by sand so the block is consumed, but take no damage. `simTick` = `stepPlayerTick` per player + `stepWorldAfter`; the server calls the same two pieces. Sand gained a `calm` event (wobble cancelled) so clients can animate it.
15. Server loop is a fixed 30 Hz timestep driven by an 8 ms poll with catch-up (max 3 ticks): a plain 33 ms interval ran at ~21 Hz on Windows. Each server tick grants every connected player 2 sim ticks of allowance (burst cap 8) and runs 2 world (sand) ticks. Commands are consumed atomically only when allowance >= ticks, so speed and dig rate are bounded to real time. `ticks` over 4 is clamped (counted), stale or replayed seq dropped, queue capped at 40 commands, malformed messages counted and the client dropped after 200.
16. Protocol additions beyond the brief: a `ready` message (client sends it after registering handlers; the server only then sends `welcome` + chunks, because messages sent from `onJoin` can arrive before colyseus.js handlers exist), `unsub` for chunks leaving the interest area, `join` option `simVersion` (mismatch rejected). Own stats travel as a flat array (`ST` layout), other pods as flat 5-number records, tiles as `[x, y, tile | aux << 8]` triples. `tiles`, `sand` and `ev` are sent before `snap` each tick so reconciliation sees the up-to-date world.
17. Interest: a player is subscribed to the 5x5 chunks around the pod's chunk (>= 32 tiles each way), recomputed only when the pod changes chunk; a reverse index chunk -> players routes deltas and sand events. Other pods are sent within 30 tiles on each axis; disconnected pods are not shown. Unmodified chunks nobody is subscribed to are evicted every 300 server ticks (diffs are kept). The client deletes a chunk from its world on `unsub` (it regenerates from the seed if needed).
18. Prediction (`shared/predict.ts`): the Predictor removes dug tiles locally, remembers them per command seq, and before every replay restores the unacked ones, so replays re-dig identically. Wallet and score are never predicted; they come from snapshots. Radar is optimistic on the client (scan from its own world); the server enforces the cooldown.
19. Reconnect: the token is a random string in localStorage plus the last room id. A non-consented leave keeps the player record for `reconnectWindowMs` (60 s, configurable) with the pod frozen and out of the sand sim; it stays on the leaderboard and is hidden from others. On reattach the input seq counters reset (the new client starts at seq 1), and a pod buried by sand meanwhile is respawned. The same token opened twice kicks the older connection. Consented leave removes the player at once. If the room has vanished (server restart) the client asks the user to reload instead of mixing worlds.
20. Rooms: `maxClients` 30, `autoDispose` off; an empty room is disposed after `roomIdleMs` (10 min). The 31st join gets a second room from Colyseus matchmaking. Server runs under `tsx` (shared is TypeScript source); `build` for the server is a typecheck. Colyseus pinned to 0.16 (`@colyseus/core` 0.16.24: 0.16.25+ ships an unresolved `workspace:` dependency).
21. Tests run with vitest `pool: 'threads'`: the forks pool crashed on IPC serialisation with websocket traffic in the server tests.

## WP4 (death, shop, leaderboard, heal)
22. Death/respawn audited end to end (shared SimPlayer timers, server events, client overlay) and covered by a server test; sand hurts any pod including the dropper, no pvp damage, no pod collisions. Dead pods are flagged `OF_DEAD` (others stop drawing them), invulnerable ones `OF_INVULN` (blinking).
23. Shop: `buy` is decided only from server state (known kind, alive, per-player cooldown `net.buyCooldownTicks` = 3 server ticks, then `buyUpgrade`, wallet only). The verdict returns in `ev` as `EV_BUY [kindIndex, code]` (BUY_OK/FUNDS/MAX/DEAD/BAD/COOLDOWN); the new wallet/levels arrive in the next snapshot. The client no longer pre-checks funds or changes anything locally; the shop shows the verdict text. Unknown kinds count as protocol violations.
24. `highScore = max(highScore, score)` is applied in shared `onDug` (live), so it never decreases and `die` only resets the rest. Leaderboard ranks by highScore only (ties by player id), top 3 as `[nick, high, id]`, plus own `rank`, `hi`, `sc`; disconnected players inside the 60 s window stay listed; sent every 30 server ticks. Client marks "me" by id, not nickname.
25. Heal ore respawn (`apps/server/src/healSpawner.ts`, tuning `T.healRespawn`): every 15 server ticks one attempt on the next chunk of a round-robin ring (rebuilt every 150 ticks from the chunks players are subscribed to, filtered to chunks already generated; never generates or scans the world). Per chunk bookkeeping = attempt counter + indices of respawned tiles still alive (cap 3 alive). Tile index = hash(seed, chunk key, counter, salt); only DIRT/ROCK at row >= healMinRow is replaced; skipped within 28 tiles (each axis) of any pod, which exceeds viewport and light. Goes through `World.set`, i.e. the normal tile delta path. Natural heal tiles do not count toward the cap.
26. Mining heal ore stays in shared `onDug` (+50% max HP, no wallet/score); the server also sends `EV_HEAL` so the client can show green particles and "+HP" at the pod. Client handles room-full and timeout errors with friendly start-screen messages.

## WP5 (abuse protection, load test)
27. Limits (`apps/server/src/limits.ts`, tuning in `T.net`): per connection token buckets per message type (`in` 40/s burst 60 against ~30/s sent by the client; `buy` 5/s burst 10; `radar` 2/s burst 4; `ping` 2/s burst 6; `ready` 2 per 10 s). A message over its bucket is dropped and counts as a violation, as does any malformed payload or unknown type; more than 200 violations (leaky: 10 forgiven per second) removes the player and closes the connection with 4404. Websocket frames are capped at 1 KB (`maxPayload`; ws closes the socket above it). Handlers run inside try/catch. Colyseus looks handlers up in a plain object, so a message type like `constructor` threw inside the socket callback (found by the fuzz test); the room now uses a prototype-less handler table. Speed and dig rate are still bounded by the per-tick allowance, the queue by 40 commands, `ticks` clamped to 4 (tests flood the server and check the consumed ticks).
28. Join limit: 10 joins per 60 s per address (`JOIN_LIMIT` env overrides, e.g. for the load test), in memory only. The key is a salted SHA-256 prefix (random per-process salt), entries are swept when their window ends, nothing is logged or persisted. Forwarded headers are honoured only with `TRUST_PROXY=1` (last entry, the one the proxy appended); otherwise they are overwritten with the socket address before Colyseus reads them. Global cap: creating a room fails with 4290 when more than `MAX_ROOMS` (20) exist. Nicknames were already validated server side (type, length, control characters, blocklist). Logs carry only room ids, counts and tick stats (`index.ts` prints them every 60 s); `GET /stats` returns the same aggregates (tick avg/p95/max, snapshots sent, rooms, players), `?reset=1` clears them.
29. Load test: `npm run loadtest -- --bots 30 --seconds 30 --url ws://localhost:2567` (`apps/server/scripts/loadtest.ts`, starts an in-process server if none answers; against an external one set `JOIN_LIMIT` high). Bots use the shared Predictor, mostly dig down, move sideways, thrust, buy affordable upgrades and use radar. Exit code 1 if p95 tick > 20 ms or a bot failed.
    Result (30 bots, 30 s, in-process server on the same machine, Windows): server tick avg 1.82 ms, p95 2.99 ms, max 7.0 ms (900 ticks); 30.0 snapshots/s per client; downstream 7.3 KB/s per client (max 8.8), 218 KB/s total; upstream 0.83 KB/s per client, 25 KB/s total; prediction error mean 0.0001 tiles, max 1.0 tile (a respawn/sand correction); 0 join failures, 0 bot errors, 1 death. Both budgets (20 ms, 200 KB/s) hold by a wide margin, so no optimisation was needed.
